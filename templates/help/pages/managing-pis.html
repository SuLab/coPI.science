Managing PIs and lab bots

Each PI in Blackbird has a research profile, built from their publications. A PI you add with Add PI also gets a lab agent: a Slack bot that speaks for the lab in the simulation. A PI who signed in on their own has no lab agent until you add them or they request one themselves. As a manager you add PIs, check what their profile and publication list say, and take each lab bot from Pending to Active. All of this happens on the PIs page, on each PI's own page, and on the Slack Bots page. Grants, industry interest and companies are covered in Grants, industry interest and companies.

Adding a PI

At the top of the PIs page is the Add a PI by ORCID iD form. It has these fields:

  • Add a PI by ORCID iD: the PI's ORCID iD, written like the placeholder in the field. You can also paste the address of their ORCID page.
  • Name (only if ORCID shows none): leave it blank unless the PI's public ORCID record shows no name. When ORCID has a name, that name is used and anything typed here is ignored.

Press Add PI. Blackbird reads the PI's public ORCID record and creates:

  • a PI account with the name, institution and department from ORCID, and the email address when ORCID shows one;
  • the PI's JHU tenure start, when ORCID lists a current Hopkins position with a start year;
  • a queued profile generation, which gathers the PI's publications and writes the research profile;
  • a lab agent with the status Pending. A pending bot cannot post or take part in the simulation until its Slack bot is installed and it is activated.

You then land on the new PI's page.

If the iD belongs to a PI who signed in to Blackbird on their own before anyone added them, that account is adopted instead of refused: its lab agent is created, its profile generation is queued if it has no profile yet, and a message says "This PI already had an account (they signed in with ORCID); their lab agent has been created."

Add PI always creates a lab bot. To add a manager or reviewer, use the Staff page instead (see Adding a staff account).

If Add PI refuses

The form shows one of these messages next to the button, and nothing is created:

  • "That doesn't look like an ORCID iD": the text is not an ORCID iD, or its last character (the check digit) does not match the rest of it. Check it against the PI's ORCID page.
  • "A user with that ORCID already exists.": the iD already belongs to a PI who has a lab agent, to a staff account, or to an account whose access is turned off. Find the PI in the list, or ask an admin.
  • "Could not fetch that ORCID record — check the iD and try again.": Blackbird could not read a public ORCID record for that iD.
  • "This ORCID record shows no public name — enter the PI's name and add again.": the iD is filled in again for you; type the PI's name in the second field and press Add PI.
  • "Names may contain letters, spaces, hyphens, apostrophes, periods and commas": the name you typed has other characters or is too long.
  • "Another PI was added at the same moment — please try again.": press Add PI again.
  • "Could not create the PI — see the server log.": ask an admin.

Profile status and agent status

The PIs list has status columns that only staff see. The Profile Status filter above the list uses the same words as the Status column.

Status (the research profile)

  • No Profile: no profile has been stored yet, or the stored profile has no research summary and no profile generation is queued or running. A newly added PI shows No Profile while their first generation runs, and so does a PI whose generation failed.
  • Generating: a profile is stored but has no research summary yet, and a profile generation is queued or running.
  • Complete: the profile has a research summary. A PI whose complete profile is being regenerated still shows Complete.
  • Pending draft: a regeneration produced a draft that is waiting for you to accept or discard it (see Pending drafts).

Agent (the lab bot)

  • Not requested: the PI has no lab agent. This is usually a PI who signed in on their own and was never added; adding them with Add PI creates the agent.
  • Pending: the agent exists but is not live. The list does not say whether its Slack bot is installed yet; the PI's page and the Slack Bots page do.
  • Active: the bot takes part in the simulation.
  • Muted: the bot is out of the simulation (see Muting and unmuting).
  • Suspended: an admin has suspended the bot. A manager cannot change a suspended bot; ask an admin.

The Claimed filter and column show whether the PI has signed in to an account that already existed (such as one Add PI created). A PI whose own sign-in created the account reads as unclaimed until they sign in again.

The Account card

The Account card at the top of a PI's page shows:

  • Email: the PI's address, marked Verified with a date or Unverified. Blackbird sends no verification email: an address is verified when a staff member vouches for it. Next to an unverified address is a Mark verified button. Changing the address later, in Edit Profile or by the PI, makes it unverified again.
  • Name: this row appears only when the name taken from ORCID had characters Blackbird does not allow and was cleaned. It reads "Cleaned from its ORCID/OAuth form on …; check the spelling." Correct the name in Edit Profile if it is wrong.
  • ORCID, Institution and Department.
  • Onboarding Complete: Yes once the PI has signed in and saved their own profile on the onboarding page. That save is the only thing that sets it; nothing a manager does on this page changes it, so a PI you added reads No until they complete onboarding themselves.
  • Claimed At: when the PI first signed in to an account that already existed, for example one created by Add PI. It reads Unclaimed until then. A PI whose own first sign-in created the account stays Unclaimed until their next sign-in.
  • Joined: the date the account was created.

Mark verified records that you vouched for this address, under your name, and the page then says "Email address marked verified." There is no button to undo it. Only press it when you know the address is the PI's.

Editing a profile

The Edit Profile form appears once the PI has a profile. Before that the page shows a Details card saying "The Edit Profile form appears once the profile exists."

The form has these fields:

  • Display Name: a change also renames the lab agent in the simulation. The Slack app's display name is not renamed; the note under the field says so, and it has to be renamed in Slack. The name is also the search key for the PI's grants, industry evidence and company discovery, and the name the next profile generation searches PubMed with and matches against each paper's authors. Saving a new name queues no refresh on its own; it takes effect at the next generation, or sooner for companies when you press Find companies, or for grants when you press Unpin.
  • Email, Institution and Department. The stored institution is what the next generation searches PubMed with, together with the name; with no institution, that name search is skipped. A generation fills Institution and Department from ORCID only where they are blank.
  • Research Summary.
  • Techniques & Methods, Model Systems, Disease Areas, Key Molecular Targets and Keywords: lists of separate items. The words in these lists decide which Slack topic channels the lab agent joins, so editing them can change where it posts. The next industry scan matches patents against Keywords, Key Molecular Targets and Disease Areas, and trials against Disease Areas.
  • JHU tenure start (year), described below.

Press Save Changes. The page says "Profile saved."

JHU tenure start

The tenure start is the year the PI's Hopkins work begins. Publications from that year on normally ground the profile and the lab agent's publication list, with the exceptions below, and it also scopes the PI's grants and industry score. Blackbird derives it when none is recorded; correct it here if it is wrong.

  • Leaving the field blank leaves the year unchanged.
  • A recorded year always wins and is never derived again. A year from the older curated list counts as recorded. With none, a profile generation tries these in order: a current Hopkins position on the PI's ORCID record that has a start year, then the earliest paper the PI's ORCID record or PubMed's ORCID field confirms and on which the PI's own affiliation is Hopkins.
  • The profile and the persona's publication list use the PI's whole career, not just the window, when there is no year at all, and also when a year is set but only a few papers fall in the window. In that second case the PI page's publication list, headed "Publications (JHU tenure, since …)", still shows only the window.
  • When no year is recorded but the last profile run worked one out from an incomplete set of papers, or without being able to read the ORCID record, an amber note under the field shows that provisional year. Enter it in the field to confirm it. While a year is only provisional, the profile, the persona and the grants use it, but the PI page's publication list is headed "Publications (full career — no JHU tenure start recorded)" and shows the whole career, and the industry score does not use it.
{% call careful() %}

Saving changes the PI's live profile:

  • it saves a new profile version and rewrites the persona, the text the lab agent works from, and records a persona revision under your name;
  • a changed tenure start also queues a full profile regeneration, which refreshes the PI's grants and industry evidence and runs company discovery again;
  • once you have changed a text field, a later regeneration no longer overwrites your edit: it waits as a Pending draft instead.

There is no undo button. To reverse an edit, edit the profile again.

{% endcall %}

A save is refused while a profile generation is queued or running ("Profile is being generated — try again shortly."), and when someone else saved the profile after you opened the page ("This profile changed while you were editing it …"). In the second case, reload the page and make your change again. It is also refused when the email address belongs to another account ("That email address is already in use by another account."), and when the tenure start is not a plain year; the message asks for a year, or a blank field to leave it unchanged.

How papers are found and kept

Each profile generation looks for the PI's papers in these places:

  • the works listed on the PI's ORCID record;
  • the works OpenAlex holds for the PI's ORCID iD;
  • the PubMed papers that carry the PI's ORCID iD;
  • PubMed, by the PI's name at the institution recorded for them. This search is skipped when the PI has no institution.

PubMed supplies the stored title, abstract, journal and year of every paper it holds. A paper is anchored when the PI's ORCID record, or the PI's ORCID iD on the paper's PubMed record, ties it to the PI (see Anchored paper). An anchored paper is stored without review. A paper found only by OpenAlex or the name search has no anchor and becomes a candidate paper (see Reviewing papers). Storage covers the PI's whole career; the tenure start decides which papers the profile and persona are written from. The overview of every data source is in Where the data comes from.

The identity check

Before a paper is stored or offered, it has to pass a check that it is the PI's:

  • the PI has to appear on the paper by name as an individual author. Accents, letters such as ø, æ and ł, hyphens, spaces and apostrophes are compared alike. One part of a double surname matches the whole ("Garcia" for "Garcia-Lopez"), but never a particle such as "de" or "van" on its own. A name recorded as "Surname, Given" is read that way, and initials written together ("JD") count as initials;
  • editorials, comments, letters, news items, corrections, expressions of concern, biographies, retraction notices, retracted papers and papers credited only to a group are left out;
  • a paper found only by the name search, one on which the PI's first name appears only as an initial, or one on which several authors match the PI's name, is also checked against the matched authors' affiliations when no ORCID anchor confirms it, and may be left out when no affiliation matches the recorded institution;
  • a paper whose authorship cannot be confirmed is left out. It is not offered as a candidate, and no page shows it;
  • papers published under a former surname never match;
  • a paper the PI's ORCID record or PubMed's ORCID field lists is kept in three further cases: when PubMed cuts its author list short before the PI; when the only matching author carries a different ORCID iD; and when PubMed records the PI's surname and given name the wrong way round. Author entries PubMed marks as invalid are ignored.

A paper that is missing from every list usually failed this check. Check the PI's name, institution and ORCID record.

Copies and earlier versions

Copies of one paper merge into one: two records with the same title, or two that PubMed links as versions of one work (a preprint and its published version, or an article and the version that updates or supersedes it). The later version is kept. A stored updated or superseded version moves to Excluded papers once its later version is stored with an ORCID anchor or accepted or kept by staff; an earlier version a person kept or accepted, or restored after Blackbird excluded it, is left alone.

Works PubMed does not index

For a PI with only a few PubMed papers in the tenure window, Blackbird also stores articles, conference papers, books, chapters and preprints that PubMed does not index, taken from the ORCID record and from OpenAlex. They are stored without review. A work that only OpenAlex attributes to the PI is stored only when the PI's authorship on it names Hopkins or an organization on the PI's ORCID record (its name as one run of words, in order), or the publisher's metadata carries the PI's ORCID iD. These works never appear in Candidate papers or Unanchored papers, and the page cannot exclude them.

Keeping papers up to date

Each generation refreshes the stored papers from PubMed. It never removes a paper, even when the searches stop finding it. Keep and Accept stop that refresh of the title, abstract, journal and year for the paper they act on (its DOI is still checked against PubMed), and so does Restore for a paper Blackbird excluded itself; a paper a person excluded and then restored is refreshed as before. Blackbird itself excludes a paper only as an earlier version, or as a copy of a paper it already holds.

Nothing refreshes a profile or its papers on a schedule. New papers arrive only with a profile generation, and these start one:

  • Add PI, unless the PI already has a profile from signing in on their own;
  • a PI's first sign-in, or an admin approving their access, when they have no profile yet, or the PI refreshing their own profile;
  • Regenerate profile and Retry profile generation;
  • a change to the JHU tenure start.

What the profile is written from

Each profile generation sends an AI model:

  • the PI's newest papers in scope that have an abstract, up to a limit, and part of each abstract. In scope means dated in the tenure window, or the whole career when there is no year or only a few papers fall in the window (see JHU tenure start above);
  • the methods sections from PubMed Central of some of the newest open-access papers. The PI page's publication list marks a paper "Methods ✓" when methods text was stored for it. "No methods fetched" usually means nobody looked, because the paper was not among those checked or is not open access; it does not mean the paper has no methods (see Methods ✓, No methods fetched);
  • the PI's grant lines, active and past (see Grant lines). On a PI's first generation these are the ORCID fundings only, because NIH awards are looked up after the profile is written;
  • the PI's name, institution, department and ORCID website.

The text it writes has to pass quality checks: a summary within the length limit, enough techniques, and at least one disease area. A text that fails is retried with the limits restated. If it fails again, it never replaces a stored profile that has not failed the checks: the generation keeps that profile, and only the papers are updated. The same happens when the new text was written from no abstracts but the stored profile was written from some. Otherwise the new text is saved, and nothing on the PI's page marks it as having failed the checks. If a person has edited the profile since its last generation, the result waits as a Pending draft instead, marked "failed the quality checks" when it failed. What each AI agent later sees of the profile is in What each AI agent sees.

Reviewing papers

The Corpus and profile review card lists the papers that need a person's decision. Unanchored papers may belong to someone with a similar name.

Candidate papers

The card's note reads: "Found only by OpenAlex or the name search, with no ORCID anchor. Accept stores the paper. A rejected paper is not offered again, but a later generation stores it if the PI's ORCID record or PubMed's ORCID field confirms it." Candidates are not part of the profile until you accept them. A pending candidate that gains an ORCID anchor is stored at the next generation without a decision from you.

Each candidate row shows stages followed by codes such as s2,s4. They name the searches that found the paper: s1, the PI's ORCID record; s2, OpenAlex; s3, PubMed's ORCID field; s4, the PubMed name search at the institution. A candidate can show only s2 and s4, because s1 or s3 would have anchored it (see Stages).

  • Accept fetches the paper from PubMed and adds it to the PI's papers, and the page says "Paper added to the corpus."
  • Reject stops the paper being offered again, and the page says "Paper rejected; it will not be offered again." If the PI's ORCID record or PubMed later ties the paper to the PI, the next generation stores it anyway.
{% call careful() %}

Reject has no undo button: the page has no way to bring a rejected paper back, and it is not offered again, although a later generation stores it if the PI's ORCID record or PubMed's ORCID field confirms it. Accept has no undo button either. Open the PMID link and check the authors before you decide.

{% endcall %}

Unanchored papers

Papers already stored for the PI that a later generation found again without an ORCID anchor, and that no one has kept, accepted or excluded.

Only papers on this list can be excluded from the page. A wrong paper that the PI's ORCID record confirms, or a work stored without a PubMed record, has no Exclude button, and no page in the Workspace can exclude it.

  • Keep marks the paper as checked; the page says "Kept." It changes nothing the profile says, but the paper leaves this list, is no longer offered for Exclude, and later profile runs do not exclude it.
  • Exclude removes the paper from the profile and the persona; Blackbird ignores it everywhere from then on. The page says "Paper excluded."

Excluded papers

The collapsed Excluded papers list shows every excluded paper, with the time it was excluded. It can also hold papers Blackbird excluded itself, such as an earlier version of a paper or a work stored without a PubMed record that PubMed has since indexed. Restore puts a paper back, and the page says "Paper restored to the corpus."

{% call careful() %}

Accept, Exclude and Restore each rewrite the persona straight away and record a persona revision. The research summary itself changes only at the next profile generation. Exclude can be undone with Restore; Keep cannot be undone.

Pending drafts

When someone has edited a profile's text since its last generation, a new generation does not overwrite that edit. Its result waits on the PI's page under Pending draft, and the PIs list shows Pending draft. The card shows when the draft was made, marks a draft that "failed the quality checks", and lists each field that differs, with the Stored and Draft text side by side.

  • Accept draft writes the draft into the profile as a new version and rewrites the persona. The page says "Draft accepted."
  • Discard draft drops the draft and leaves the profile as it is. The page says "Draft discarded."

A draft is stale when the profile changed after the draft was made. The card then says "The profile changed since this draft was made; discard it or regenerate." and offers only Discard draft. Accepting is also refused while a profile generation is queued or running.

{% call careful() %}

Neither Accept draft nor Discard draft can be undone. After accepting, edit the profile to change it back; after discarding, regenerate to get a new draft.

{% endcall %}

Regenerate and Retry profile generation

These buttons queue a new profile generation.

Regenerate profile

Regenerate profile, in the Corpus and profile review card, queues a generation for any PI. The button is disabled while a generation is queued or running, and for a while after one finishes; the text under it gives the reason. When it is accepted the page says "Profile generation queued. A profile edited since its last generation gets a draft to review."

Retry profile generation

Retry profile generation appears at the top of the PI's page only while the lab agent is Pending, and only when the profile is not ready to activate:

  • the last generation failed for good ("Agent pending — profile generation failed after … attempts.");
  • no profile has been generated yet ("Agent pending — no profile has been generated yet.");
  • the profile is not grounded in any publication abstract, or has no research summary ("Agent pending — the profile is not grounded in any publication abstract."). This often means the name or ORCID iD is wrong: check both, and correct the name in Edit Profile first.

It is not offered while a generation is queued or running. When it is accepted the page says "Profile generation queued."

For an account whose access has been turned off, either button says "This account's access is denied; no profile is generated." and nothing is queued.

{% call careful() %}

Both buttons start a full profile generation, which cannot be cancelled from the page. If the profile was edited since its last generation, the result waits as a Pending draft. Otherwise the new text replaces the profile, unless the stored profile passed the quality checks and the new text failed them twice or was written from no abstracts while the stored one had some; then the stored profile stays and only the papers are updated (see What the profile is written from).

Every successful generation also re-reads the PI's ORCID fundings, refreshes the PI's grants and industry evidence, and runs company discovery again.

{% endcall %}

The persona file

The persona is the text the lab agent works from: the PI's profile, publications and grants. Blackbird rewrites the persona file whenever something in it changes. Its publication list holds the newest papers in scope, each as a title, journal and year with a DOI or PubMed link; the lab agent gets no abstracts. What each AI agent sees is in What each AI agent sees.

If a rewrite failed, or the saved file no longer matches the profile, the Corpus and profile review card says Persona file out of date, with the time of the failed write when there was one. Press Re-export to write it again. The page says "Persona file re-exported." If it says "Re-export failed; see the ERROR log.", ask an admin. "This PI has no agent or profile to export." means there is nothing to write yet.

{% call careful() %}

Re-export rewrites the persona file the lab agent reads and records a persona revision under your name. It changes nothing in the profile.

{% endcall %}

The Persona revisions card lists the most recent versions of the persona, newest first. Each shows when it was written, how it was changed, who changed it ("system" for an automatic change) and a short summary. view text opens the full persona as it was then. A PI with no lab agent has no revisions.

The Jobs table

The Jobs table at the bottom of the PI's page lists the background work queued for this PI, newest first, such as profile generation, grant refreshes, the industry scan and company discovery. Its columns are Type, Status, Attempts (attempts made out of attempts allowed), Enqueued and Completed.

  • Pending: waiting to run. A job whose attempt failed waits here before it is tried again, with the error shown under it.
  • Processing: running now.
  • Completed: finished.
  • Dead: it failed on every attempt it was allowed, or failed in a way a retry cannot fix. The red line under it shows the start of the last error. For a dead profile generation, use Retry profile generation or Regenerate profile.

Installing the Slack bot

While the lab agent is Pending, the top right of the PI's page shows where it stands and the next step. Once the profile is done the line reads "Agent pending — Awaiting Slack install." and keeps saying so after the install; the button below it shows the real next step. With no Slack bot installed the button is Install Slack bot. It creates a Slack app for this lab and takes you to Slack's install screen. Approve the install there.

Slack then sends you back to the PI's page, which says "Slack bot installed — the token is saved on this PI's agent. Activate the agent to bring it live." The button now reads Activate agent.

If creating the Slack app fails, the PI's page shows a message starting "Slack provisioning failed:" with the reason. If the install fails or is cancelled after you reach Slack, you come back to the PIs list instead, with that message at the top. Finish an install from the same account that started it: otherwise the return is refused with "This install was started by a different account."

{% call careful() %}

Install Slack bot creates a real Slack app in the workspace. Blackbird cannot remove a finished install from its pages. Pressing Install Slack bot again before an install finishes deletes the earlier, unfinished Slack app and creates a new one.

Activating a lab bot

Activate agent takes a pending bot live. Before it does, Blackbird checks that:

  • the Slack bot is installed;
  • a profile exists and is grounded in the PI's publication abstracts;
  • the profile has a Research Summary;
  • the latest profile generation did not fail for good;
  • the persona file exists and has a Research Summary;
  • the account is a PI account;
  • the lab can be connected to the hub, BlackbirdBot.

If any check fails, nothing changes. The page shows "Activation refused — this PI's profile is not ready:" with the list of reasons, or a message starting "Activation refused:". Fix the profile, or retry profile generation; if a reason names the persona file, press Re-export in the Corpus and profile review card; then activate again. Managers cannot activate past these checks. Only an admin can override the profile checks; nobody can override the persona file, account or hub checks.

When activation succeeds, a green banner says "Agent activated" and that the running simulation picks the agent up on its next roster sync. You do not need to restart anything.

{% call careful() %}

Activating puts the bot on the roster of the running simulation, where it starts taking part in conversations. To take it out again, use Mute.

{% endcall %}

Muting and unmuting

An Active bot has a Mute button at the top of the PI's page and on the Slack Bots page. A Muted bot has Unmute instead.

  • Mute takes the bot out of the simulation at the next roster sync. The page then shows when it was muted.
  • Unmute makes the bot active again. It runs the same checks as Activate agent and also needs the Slack bot to be installed. If a check fails, the bot stays muted and the page says why, for example "This agent can't be unmuted yet: its profile doesn't pass the activation checks."

A bot also shows Muted when an admin took it out of the simulation. Unmute works the same way however the bot was muted. Pending and suspended bots cannot be muted. A pending bot shows its install or activate control instead; for a suspended bot the page says "Agent is suspended — mute is only available for an active or already-muted agent."

{% call careful() %}

Mute and Unmute change who takes part in the running simulation. Each undoes the other.

{% endcall %}

The Slack Bots page

The Slack Bots page lists every PI lab bot in one table, with how many are active, pending and muted at the top. Its columns are:

  • PI: a link to the PI's page. A bot with no PI account shows "(no linked PI)" and has no actions.
  • Bot: the bot's name and its id.
  • Status: Active, Pending, Muted, or another status set by an admin.
  • Slack token: installed or not installed.
  • Actions: the same buttons as on the PI's page: Install Slack bot, Activate, Mute or Unmute.

Each action does exactly what it does on the PI's page, with the same checks, and then takes you to that PI's page, where any message appears. Install Slack bot goes through Slack's install screen first; if the install fails or is cancelled there, you land on the PIs list with the message instead.

{% call careful() %}

The Careful boxes in Installing the Slack bot, Activating a lab bot and Muting and unmuting apply to these buttons too.
